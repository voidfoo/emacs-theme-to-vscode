# UX review: full theme corpus

**Reviewed:** 2026-11-13  
**Scope:** All Emacs source dumps, generated VS Code themes, current converter scope mappings, and extension theme metadata.

## Executive summary

Reviewed all **141** source/generated theme pairs. There are no missing generated themes or manifest entries. The extension manifest's `uiTheme` agrees with each generated theme's light/dark type. The current converter changes have removed inferred token rules and the previously misplaced workbench color IDs from token scopes.

**The `support.type` leak is still present.** The current face map assigns the broad `support.type` selector to both `font-lock-builtin-face` and `font-lock-type-face`. Every generated theme has at least one such rule, and nine themes give one or both faces an italic style. Because VS Code's inspector can report nested scopes such as `support.type.property-name.json`, those rules can style JSON property-name/string tokens even though their Emacs string face is not italic.

The corpus-wide contrast scan also flags a large number of token foreground/background combinations for low contrast. Treat these as review candidates, not automatic failures: syntax roles and colored backgrounds vary, and the scan does not replace visual inspection.

## Findings

### High — `support.type` still leaks broad type/builtin styling

The current map still includes `support.type` in both the builtin and type face scopes ([faceToScopeMap.js](../../tools/converter/faceToScopeMap.js#L36), [faceToScopeMap.js](../../tools/converter/faceToScopeMap.js#L56)). The converter emits mapped scopes in `buildTokenColors` ([convertTheme.js](../../tools/converter/convertTheme.js#L302)).

Corpus results:

- All **141/141** generated themes include at least one `support.type` rule; **280 rules** total.
- **9 themes** have italic styling on a face mapped to `support.type`:
  - `doom-earl-grey`
  - `doom-ephemeral`
  - `doom-flatwhite`
  - `doom-monokai-classic`
  - `doom-oksolar-light`
  - `doom-plain`
  - `doom-plain-dark`
  - `doom-solarized-dark-high-contrast`
  - `doom-solarized-light`
- The leak can affect color in all 141 themes, not just italics; the italic symptom is limited to those nine.
- The current regression test verifies that token scopes exclude VS Code workbench color IDs, but it does not prevent broad TextMate scope collisions ([convertTheme.test.js](../../tools/converter/convertTheme.test.js#L75)).

**Recommendation:** Narrow or remove generic `support.type` from the affected face mappings, then add a scope-stack regression test using the observed JSON scopes (`support.type.property-name.json`, `string.json`, and their enclosing scopes). Verify both style and foreground in VS Code's scope inspector. Consider whether `font-lock-builtin-face` should retain `support.function`/`support.class` while dropping `support.type`; for `font-lock-type-face`, prefer type-specific selectors that do not match property-name scopes.

### Positive — Scope noise and workbench/TextMate separation improved

- **0 inferred token rules** appear in the generated corpus.
- **0 token rules** use workbench color IDs. Those UI colors are represented in the theme `colors` section instead.
- Token rules average **28.8 per theme**; the reviewed source and generated files are valid JSON.

These are improvements over the earlier converter behavior. They do not address the separate broad `support.type` collision above.

### Positive — Theme catalog metadata is consistent

- All **141/141** source themes have a generated counterpart.
- All **141/141** generated themes have a corresponding extension manifest entry.
- Theme `type` and manifest `uiTheme` agree for every theme.
- Corpus distribution: **93 dark**, **48 light**.

### Medium — Syntax foreground contrast needs selective follow-up

Contrast screening used each token rule's foreground against its explicit six-digit background, or the theme's editor background when none was specified. Using **4.5:1** as a reference threshold:

- **766** token-rule color pairs across **109/141** themes are below 4.5:1.
- The lowest examples include:
  - `leuven-dark` trailing whitespace: **1.14:1**
  - `leuven` trailing whitespace: **1.18:1**
  - `doom-ayu-light` documentation face: **1.41:1**
  - `doom-wilmersdorf` mismatched-parenthesis face: **1.42:1**
  - `doom-ayu-light` comment face: **1.63:1**
- Default editor foreground/background contrast is above 4.5:1 for **140/141** themes. `doom-manegarm` is **4.17:1**.

**Recommendation:** Prioritize readability of comments, documentation, and active warning/highlight states in visual review. Avoid blindly adjusting every low-contrast token: some backgrounds are intended as subtle decoration, and theme fidelity is an explicit product goal. If changing source fidelity is undesirable, consider a documented high-contrast variant or accessibility guidance.

## Method and limitations

The audit compared all 141 `emacs-definitions/emacs-*.json` files with `vscode-extension/themes/*.json` and `contributes.themes` in the extension manifest. It also checked generated token scopes, style settings, and static foreground/background ratios. Static contrast values do not account for editor rendering, font size/weight, alpha blending, or whether the token is essential text; manually inspect representative code and JSON in VS Code before changing theme palettes.

No theme data or converter files were modified for this review.

## Validation

- Current converter regression tests: **8 passed**.
- In-memory conversion comparison: **141/141** generated files exactly match the current converter output; no files were written during this check.
