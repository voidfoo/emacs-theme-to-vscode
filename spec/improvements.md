# Converter Improvements — Implementation Brief

Findings from a review of the Emacs → VS Code theme pipeline, with concrete
recommendations. Each issue is self-contained; suggested PR grouping and order
are at the end.

## Context

- **Dumper**: `tools/dumper/dump-theme.el` (Emacs 30+) writes
  `emacs-definitions/emacs-{theme}.json` (`{ face: { fg, bg } }`).
- **Converter**: `tools/converter/convert.js` (ESM, `// @ts-check`, Node 24)
  writes `vscode-extension/themes/{theme}.json` and rewrites
  `contributes.themes` in `vscode-extension/package.json`.
- Supporting files: `faceToScopeMap.js` (face → TextMate scopes),
  `namedColors.js`, `utils.js` (color math), `analyze-colors.js`.
- Spec: `spec/main.md`.

### Working rules

- Commands (run in `tools/converter`): `pnpm install`, `pnpm check` (tsc),
  `pnpm format` (prettier), `node convert.js` (regenerates all themes).
  Use `npx pnpm@10` if pnpm is not available; do not install pnpm globally.
- Keep files ESM + `// @ts-check`; keep `pnpm check` passing; format with prettier.
- After any converter change, run `node convert.js` and commit the regenerated
  `vscode-extension/themes/*.json` and `package.json` in the same PR.
- `emacs-definitions/*.json` can only be regenerated by a human running Emacs
  with all themes installed (built-in, doom-themes, ef-themes, modus-themes).
  Do not hand-edit them.
- Add a `vscode-extension/CHANGELOG.md` entry for user-visible theme changes.
- Baseline (verified): running `node convert.js` on `main` reproduces all
  committed theme files exactly; only `package.json` differs (see issue 3).

## 1. Font styles (bold/italic/underline) are never exported

**Finding**
- The dumper only exports `:foreground` / `:background`
  (`dump-theme.el`, the `dolist (face all-faces)` block).
- `convert.js` has handling for `faceData.weight`, `faceData.slant`,
  `faceData.underline`, but no dump contains those keys, so it never runs.
- Latent bug in that code: `if (faceData.underline) settings.fontStyle = "underline";`
  overwrites bold/italic instead of combining them.
- Faces with a style but no color are skipped entirely by the dumper
  (`when (or fg bg)` guard).

**Recommendation**

Dumper — export normalized boolean flags (only when true):

```elisp
(let* ((weight (face-attribute face :weight nil t))
       (slant  (face-attribute face :slant nil t))
       (ul     (face-attribute face :underline nil t))
       (strike (face-attribute face :strike-through nil t))
       (bold   (memq weight '(semi-bold demibold bold extra-bold ultra-bold heavy black ultra-heavy)))
       (italic (memq slant '(italic oblique reverse-italic reverse-oblique)))
       (ul     (and ul (not (eq ul 'unspecified))))
       (strike (and strike (not (eq strike 'unspecified)))))
  ...
  (when bold   (puthash "bold" t attrs))
  (when italic (puthash "italic" t attrs))
  (when ul     (puthash "underline" t attrs))
  (when strike (puthash "strike" t attrs)))
```

- The trailing `t` (INHERIT) argument already resolves `:inherit` chains.
- Store a face if it has any of fg/bg/bold/italic/underline/strike.
- Optional: handle `:inverse-video` by swapping fg/bg (used by some built-in
  themes for `region` / `mode-line`).

Converter — replace the existing style block:

```js
const styles = [];
if (faceData.bold) styles.push("bold");
if (faceData.italic) styles.push("italic");
if (faceData.underline) styles.push("underline");
if (faceData.strike) styles.push("strikethrough");
if (styles.length) settings.fontStyle = styles.join(" ");
```

Remove the old `weight` / `slant` / `underline` handling.

**Open decision (ask the user before re-dumping)**
modus-themes and ef-themes gate bold/italic behind user options
(`modus-themes-bold-constructs`, `modus-themes-italic-constructs`,
ef-themes equivalents) that default to `nil`. Either dump with defaults
(faithful) or enable them before dumping (italic comments, bold keywords).
Document the choice in `spec/main.md`.

**Acceptance**
- `spec/main.md` face-export example shows the new flags.
- Converter handles the new flags; a unit test covers combined styles
  (e.g. bold + italic + underline → `"bold italic underline"`).
- Agent can implement both sides; a human must re-run `dump-all-theme-faces`
  and then `node convert.js`.

## 2. Inferred token scopes are noisy and override real mappings

**Findings**
- `inferScopes()` in `convert.js` regex-matches face names and emits an extra
  `"<face> (inferred)"` rule for each match. In `modus-vivendi.json`, 77 of
  125 token rules are inferred.
- It matches faces from other packages: `next-error` → `invalid` (and is the last
  `invalid` rule, so it wins, in every theme); `magit-keyword`,
  `git-commit-keyword`, `markdown-language-keyword-face` → `keyword`;
  `change-log-function` → `entity.name.function`. VS Code uses the last rule
  when two rules have the same scope, so correctness currently depends on the
  order faces appear in the dump.
- The only legitimate wins of inference are the newer `font-lock-*` faces
  that `FACE_TO_SCOPE_MAP` does not cover. All 28 `font-lock-*` faces exist in
  the dumps (see `emacs-definitions/emacs-modus-vivendi.json`).
  - **Correction (follow-up)**: inference also supplied the only
    `entity.name.tag` and `markup.inserted` rules (from
    `markdown-html-tag-*` and `magit-diff-added*`). These are now mapped
    explicitly: `font-lock-function-name-face` → `entity.name.tag` (as in
    `sgml-mode`/`html-ts-mode`) and `diff-added`/`diff-removed`/`diff-changed`
    → `markup.inserted`/`markup.deleted`/`markup.changed`.
- **Related bug**: ~20 entries in `FACE_TO_SCOPE_MAP` are VS Code *workbench
  color IDs*, not TextMate scopes (e.g. `region` → `editor.selectionBackground`,
  `company-tooltip` → `editorSuggestWidget.background`,
  `treemacs-git-*` → `gitDecoration.*`, `mode-line` → `statusBar.*`,
  `diff-added` → `diff.insertedTextBackground`). They become useless
  `tokenColors` entries and the intended UI colors are never set.

**Recommendation**
1. Delete `inferScopes()` and the second `tokenColors.push` that uses it.
2. Add explicit mappings to `faceToScopeMap.js`:

   ```js
   "font-lock-function-call-face": ["meta.function-call entity.name.function", "support.function"],
   "font-lock-variable-use-face": ["variable.other.readwrite"],
   "font-lock-property-name-face": ["variable.other.property", "support.type.property-name"],
   "font-lock-property-use-face": ["variable.other.object.property", "meta.property"],
   "font-lock-number-face": ["constant.numeric"],
   "font-lock-operator-face": ["keyword.operator"],
   "font-lock-escape-face": ["constant.character.escape"],
   "font-lock-regexp-face": ["string.regexp"],
   "font-lock-regexp-grouping-construct": ["punctuation.definition.group.regexp"],
   "font-lock-regexp-grouping-backslash": ["constant.character.escape.backslash.regexp"],
   "font-lock-negation-char-face": ["keyword.operator.logical"],
   "font-lock-bracket-face": ["punctuation.section", "meta.brace"],
   "font-lock-delimiter-face": ["punctuation.separator", "punctuation.terminator"],
   "font-lock-punctuation-face": ["punctuation"],
   "font-lock-misc-punctuation-face": ["punctuation.accessor"],
   "font-lock-doc-markup-face": ["comment.documentation storage.type", "entity.name.type.instance.jsdoc"],
   ```

   - Skip emitting a rule when the face's fg equals the default fg and it has
     no bg/style (it would add nothing and can override parent-scope colors).
   - Watch for broad scopes stealing color from specific ones: in TextMate a
     rule matching a deeper scope wins, so `punctuation` would recolor string
     quotes. Add `punctuation.definition.string` to `font-lock-string-face`
     (and similar for other faces as needed).
3. Emit token rules in `FACE_TO_SCOPE_MAP` key order (iterate the map and
   look up the face in the theme), not dump order. Put broad rules before
   specific ones.
4. Split UI color IDs out of `FACE_TO_SCOPE_MAP` into `EDITOR_COLORS` with
   proper `fg`/`bg` targets (e.g. `company-tooltip.bg` →
   `editorSuggestWidget.background`, `treemacs-git-modified-face.fg` →
   `gitDecoration.modifiedResourceForeground`). Leave only real TextMate
   scopes in `FACE_TO_SCOPE_MAP`. This changes UI colors in most themes;
   do it as a separate PR from steps 1–3.

**Acceptance**
- No `(inferred)` rules in generated themes.
- No token rule's `scope` contains a workbench color ID (checkable with a
  regex such as `^(editor|statusBar|diff|diffEditor|gitDecoration|editorSuggestWidget|editorLineNumber|editorGutter|scrollbarSlider|breadcrumb|explorer|tree)\.`).
- Spot-check several themes in the Extension Development Host
  (`.vscode/launch.json` → "Extension") with JS/TS/Python/Markdown files.

## 3. `package.json` theme order depends on the OS; missing trailing newlines

**Finding**
- `main()` uses `fs.readdir` order. On Windows, `doom-Iosvkem` sorts after
  `doom-horizon`; the committed file has it right after `doom-1337`
  (code-unit order). Running the converter on Windows therefore changes
  `package.json`.
- `JSON.stringify` output is written without a trailing newline (package.json
  and every theme file).

**Recommendation**
- `files.sort()` (default code-unit order, matching the committed file) before
  converting.
- Append `"\n"` when writing JSON files.
- Optional: add a root `.gitattributes` with `* text=auto eol=lf` so generated
  files don't produce CRLF warnings on Windows.

**Acceptance**: running `node convert.js` on any OS produces no diff other than
added trailing newlines (first run only).

## 4. `analyze-colors.js` crashes

**Finding**: uses `__dirname` in an ESM package (`"type": "module"`), so it
throws `ReferenceError` at startup. `tsc` doesn't catch it because
`@types/node` declares `__dirname` globally.

**Recommendation**: derive the directory with
`dirname(fileURLToPath(import.meta.url))` (as `convert.js` does), add
`// @ts-check`, and add a `"analyze-colors": "node analyze-colors.js"` script.

**Acceptance**: `node analyze-colors.js` prints the list of named colors.

## 5. Dead code and duplicated logic in `convert.js`

**Finding**
- `processThemeColors()` (~170 lines) is never called. `convertToVSCodeTheme()`
  duplicates most of its fallback logic.
- Features that exist **only** in the dead function, so they are never applied:
  - `editor.selectionBackground` + `"40"` and `editor.findMatchBackground` +
    `"80"` alpha (e.g. `modus-vivendi` ships an opaque `#5a5a5a` selection).
  - `diff-hl-margin-{insert,delete,change}` → `diffEditor.*LineBackground` /
    `*TextBackground`.
  - Foreground contrast adjustment for `EDITOR_COLORS` fg targets — but it
    checks every fg against the *editor* background, which is wrong for
    e.g. `statusBar.foreground`.
- Inside `convertToVSCodeTheme()`: `detectThemeType()` is called twice
  (`type` and `effectiveType`); the default bg is computed twice
  (`effectiveDefaultBg`, `defaultBg`); the `default` face is applied three
  times (via `EDITOR_COLORS`, then again in the face loop).
- `inferScopes()` reads `faceData.default?.bg` from a single face object
  (always undefined); goes away with issue 2.

**Recommendation**
- Delete `processThemeColors()`.
- Restructure `convertToVSCodeTheme()` into small steps:
  `computeBase()` (type, defaultFg/defaultBg) → `applyEditorColors()` →
  `applyFallbacks()` → `buildTokenColors()`.
- Port into the live path: selection/find-match alpha (via the helper from
  issue 7) and the `diff-hl` mappings. Do **not** port the blanket fg
  contrast adjustment; contrast checks belong at specific fg/bg pairs
  (issue 6).
- Expect output changes from the ported features; call them out in the PR.

**Acceptance**: no unused functions; `pnpm check` passes; regenerated themes
have translucent selection/find colors and diff colors where `diff-hl` faces
exist.

## 6. Contrast math doesn't follow WCAG and can fail to converge

**Finding** (`utils.js`)
- `getLuminance()` skips sRGB gamma linearization, so `getContrastRatio()`
  is not the WCAG ratio.
- `adjustColorLuminance()` multiplies channels, so black (`#000000`) or
  near-black can never be lightened; `adjustColorForContrast()` gives up after
  a 50% change and may return a color that still fails 4.5:1.
- Neither handles `#rgb` or `#rrggbbaa`.

**Recommendation**
- Implement WCAG relative luminance (linearize each channel:
  `c <= 0.04045 ? c/12.92 : ((c+0.055)/1.055)^2.4`).
- Implement `mix(color, target, t)` and make `adjustColorForContrast()`
  binary-search the smallest `t` that mixes fg toward white (dark bg) or
  black (light bg) to reach `minContrast`. Mixing to pure white/black always
  reaches ≥ 4.5:1 against any bg, so convergence is guaranteed.
- Keep `detectThemeType()` stable: the 0.5 threshold was for the
  non-linear formula. Use "dark if contrast with white > contrast with black"
  (or relative luminance < ~0.18). Verify no theme changes `uiTheme`.
- Keep `adjustColorLuminance()` for sidebar/input shading if desired, but make
  it mix toward white/black instead of multiplying.

**Acceptance**: unit tests show `adjustColorForContrast()` always reaches the
target ratio (including fg `#000000` on a dark bg); every theme keeps the
same `uiTheme` in `package.json`.

## 7. Alpha is appended to colors by string concatenation

**Finding**: `color + "40"` / `"80"` / `"30"` / `"20"` breaks if the color is
`#rgb`, already `#rrggbbaa`, or an unresolved name (`normalizeColor()` returns
unknown names unchanged after a warning).

**Recommendation**
- Make `normalizeColor()` always return lowercase `#rrggbb` (expand `#rgb`,
  strip alpha), and throw (or warn and return `undefined` so the caller
  skips it) for unknown names.
- Add `withAlpha(color, alpha /* 0..1 */)` in `utils.js` that normalizes and
  appends a 2-digit hex alpha; use it everywhere alpha is applied.

**Acceptance**: no string concatenation of alpha in `convert.js`; tests
cover `#abc`, `#aabbcc`, `#aabbccdd`, and named colors.

## 8. No CI

**Recommendation**: add `.github/workflows/ci.yml` running on PRs and `main`:

```yaml
jobs:
  check:
    runs-on: ubuntu-latest
    defaults: { run: { working-directory: tools/converter } }
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4
        with: { version: 10 }
      - uses: actions/setup-node@v4
        with: { node-version: 24, cache: pnpm, cache-dependency-path: tools/converter/pnpm-lock.yaml }
      - run: pnpm install --frozen-lockfile
      - run: pnpm check
      - run: pnpm exec prettier --check *.js *.json
      - run: pnpm test
      - run: node convert.js
      - run: git diff --exit-code   # generated themes must be committed
```

Optionally add `"packageManager": "pnpm@10.x.y"` to
`tools/converter/package.json`.

**Acceptance**: workflow passes on `main` after issues 3 and 4 land.

## 9. No tests

**Recommendation**
- Use the built-in `node:test` runner (no new deps); add
  `"test": "node --test"` to `tools/converter/package.json`.
- `convert.js` calls `main()` when imported; move pure functions
  (`normalizeColor`, `detectThemeType`, `convertToVSCodeTheme`, style
  building) to a module (e.g. `convertTheme.js`) so tests can import them
  without side effects, and keep `convert.js` as the CLI entry point.
- Focused cases: color normalization/alpha (issue 7), contrast convergence
  (issue 6), dark/light detection for a few real dumps, fontStyle
  composition (issue 1), no `(inferred)` / workbench IDs in `tokenColors`
  (issue 2).

## 11. `color-N` handling is wrong (low priority)

**Finding**: `normalizeColor()` treats `color-123` as a hex number
(`#00007b`). In Emacs these are xterm 256-color palette indices. No current
dump contains `color-N`, so there is no output impact today.

**Recommendation**: map using the xterm palette — 0–15 standard ANSI colors,
16–231 a 6×6×6 cube with levels `[0, 95, 135, 175, 215, 255]`,
232–255 grays `8 + 10 * (n - 232)` — or throw an explicit error.
